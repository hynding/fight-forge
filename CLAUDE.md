# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

- `npm run dev` — start the Vite dev server
- `npm run build` — TypeScript typecheck (`tsc`) then production build (`vite build`); typecheck failures fail the build
- `npm run preview` — preview the production build locally
- `npm run lint` — ESLint (flat config in `eslint.config.js`) over `ts,tsx`, runs with `--max-warnings 0` (any warning fails)
- `npm run pack:sample` — bundle the sample packs in `content/samples/` into `public/packs/*.zip` (runs automatically before `dev` and `build`)
- `npm run perf` — the frame-time budget check: plays the Stress Test sample (32 enemies) in Chromium and prints frame times and draw calls, failing when the 95th-percentile frame is over 16.7 ms × `--slack` (`--headed` for a real GPU; headless uses software WebGL and is always slow). Needs Playwright, which isn't a dependency
- `npm test` — Vitest, single run. Tests live next to the code as `*.test.ts` (store and pure helpers; no DOM/WebGL environment is configured)

## Tech Stack

React 18 + TypeScript + Vite. The 3D game runtime is built on:
- `@react-three/fiber` — React renderer for Three.js (`<Canvas>`, `useFrame`)
- `@react-three/drei` — helpers (`PerspectiveCamera`, `Billboard`, `useGLTF`, `useAnimations`)
- `@react-three/rapier` — Rapier physics (`<Physics>`, `<RigidBody>`, `RapierRigidBody`, `CuboidCollider`)
- `zustand` — global game state

## Architecture

### Screen flow
[src/App.tsx](src/App.tsx) reads `gameScreen` from the zustand store and renders one of `StartMenu`, `LoadingScreen`, or `GameScene`. All screen transitions go through `setGameScreen` in [src/store/gameStore.ts](src/store/gameStore.ts).

### Single global store
All cross-component game state lives in [src/store/gameStore.ts](src/store/gameStore.ts): `playerHealth`, `score`, `enemies` (array of `{ id, type, health, maxHealth, position }`), `isGameOver`, `isPaused`, `gameScreen`, `attackTokens`, `gameId`, `levelProgress`, `showHitboxes`, and run state (`levelIndex`, `lives`, `continuesLeft`, `respawnCount`, `kos`, `runKos`, `pickups`). Components subscribe with selectors (`useGameStore((s) => s.foo)`). Avoid adding parallel state for things the store already tracks.

### Restart, pause, and game over
`App` renders `<GameScene key={gameId} />`, and `resetGame`, `startRun` and `nextLevel` increment `gameId`, so a restart or new level remounts the whole scene (fresh physics bodies, refs, and initial spawn). While `isFrozen(state)` (paused, game over, or level complete), `<Physics paused>` freezes bodies, the sim loop stops advancing, and the movement `useFrame` loops in `Player` and `Enemy` return early, so all gameplay timers are game time and freeze too. Prefer game-time timers over `setTimeout` for gameplay.

### Fixed-step simulation loop
Gameplay timers and rules run as **systems** in a fixed 60 Hz loop: [src/sim/loop.ts](src/sim/loop.ts) (`SimLoop`, `SIM_STEP`, `SYSTEM_ORDER`). `<SimLoopDriver>` (inside the `Canvas`, wrapping `Physics`) owns one loop per scene and advances it once per rendered frame unless paused or game over; each frame's delta goes through `gameStep` from [src/utils/gameTime.ts](src/utils/gameTime.ts), which clamps the huge first-frame delta after a hidden tab. Components register systems with `useSimSystem(name, SYSTEM_ORDER.x, step)` from [src/sim/simContext.ts](src/sim/simContext.ts); systems always receive `dt = SIM_STEP` and run in `SYSTEM_ORDER` (input, fighters, camera, player attack, enemy attack slots, combat, pickups, level), so combat sees a move on the step it starts. Use `loop.time` (via `useSimLoop()`) as the game clock. Timer, move, reaction and hit math live as pure functions in `src/sim` (`timers.ts`, `moves.ts`, `reactions.ts`, `combat.ts`) with unit tests.

### Attack tokens
At most `rules.maxSimultaneousAttackers` (default 1) enemies may attack the player at once. The pool lives in the store as `attackTokens` (`holders`, and a `waiting` queue), with pure, tested logic in [src/sim/tokens.ts](src/sim/tokens.ts): a free token goes to the longest-waiting enemy, so a fixed system order can't starve anyone. [src/components/CombatSystem.tsx](src/components/CombatSystem.tsx) only lets an enemy's hitbox hit the player while it holds a token (or has its own slot, as bosses do). The AI only says it wants to attack; the enemy's `enemyAttackSlot:<id>` sim system queues (`requestAttackToken`) while it's in attack position, free and out of recovery, and leaves the queue (`cancelAttackRequest`) otherwise. Getting a token throws its attack move; it holds the token for `enemy.attackSlotDuration`, gives it back (`releaseAttackToken`, or early if hit), then waits `enemy.attackSlotRecovery`. The store forgets a dead or removed enemy's token and queue place. Per-step code must read `useGameStore.getState()`, not a render-time selector, which can be frames stale. Keep attacks gated by tokens when changing enemy AI; unlimited simultaneous attackers stack damage and break balance.

### Rendering vs. simulation split
- **State (zustand)**: health, score, enemy list, screen — anything UIs read.
- **Refs (`RapierRigidBody`)**: positions and velocities — anything updated per-frame. Reading `translation()`/`linvel()` from a rigid body ref is the canonical way to get a current position. Do not mirror positions into React state for per-frame logic; it causes re-renders and lags physics.
- [src/components/GameScene.tsx](src/components/GameScene.tsx) owns the `playerRef` and an `enemyRefs: Map<string, RefObject<RapierRigidBody>>`. Refs are created with `createRef()` keyed by enemy id, and stale entries are pruned in a `useEffect` watching `enemies`.
- `playerPositionRef` (a shared `Vector3`) is copied from the player body by a `useFrame` in `CombatSystem` every rendered frame; `CameraRig` reads it in its `useFrame` and the enemy AI reads it in its sim step. Nothing mirrors it into React state.

### Moves, hitboxes and combat
Attacks are **moves** with frame data, defined by id in the content's `moves` and stepped by pure code in [src/sim/moves.ts](src/sim/moves.ts): `startup` / `active` / `recovery` seconds, `damage`, a `hitbox` (a box in front of the attacker along its facing, × its scale), the `reaction` it causes, an optional `clip` (the model plays it once per move instance), and an optional `next` move reached by a buffered press once the cancel window (`cancelFrom`, default end of active) opens. Which move a press starts is the player's **moveset** (`settings.player.moveset`, [src/sim/moveset.ts](src/sim/moveset.ts)): ordered triggers, the first match wins (`matchTrigger`), each with an `action` (or a chord of two or three pressed within `input.chordWindow`; `stepChords` holds back only actions that are in a chord), optional `when` (`ground` by default, which excludes blocking; `air`, `running` or `blocking`), `direction` relative to facing (`toward`, `away`, `up`, `down`; judged against the facing before a turn within `input.turnGrace`, and an `away` move comes out without turning round) and `cost` (`health`, never the last point, via `spendHealth`; `cooldown`). `cost` can also be `meter` (`rules.meter`: the store's `meter`, filled by damage dealt and taken in CombatSystem via `gainMeter`, spent with `spendMeter`; the HUD shows a bar when some row costs meter). The default moveset is special (50 meter) → `shockwave`, air → `jumpKick`, running → `dashPunch`, heavy → `haymaker`, else `jab` (jab → jab2 → hook → uppercut; heavy during jab, jab2 or hook branches into `haymaker`). `stepMoves` runs a fighter's moves: during a move, the press that started it chains into `next`, another press into the move's `branches` (by press key, e.g. `attack+jump`). Presses are edge-triggered, so holding J doesn't repeat. Each fighter's `MoveRunner` and `ReactionState` live on its `FighterRuntime`; while busy with either, the controller can't walk, jump or turn (`isBusy`).

[src/components/CombatSystem.tsx](src/components/CombatSystem.tsx) is the `combat` sim system. Fighters register their runtimes in the `runtimes` Map owned by `GameScene` (the player as `"player"`, enemies by id). For each fighter in a move's active frames it overlaps the hitbox with targets' hurtboxes (the collider's half extents) using `hitboxWorld` / `boxesOverlap` from [src/sim/combat.ts](src/sim/combat.ts); a move instance hits each target at most once. A hit calls `applyHit` ([src/sim/reactions.ts](src/sim/reactions.ts)): hitstun, or knockdown → getup → brief invulnerability (the `reactions` settings), sets knockback on the runtime and body, interrupts the target's move, and calls `damagePlayer` / `damageEnemy`. `damageEnemy` in the store removes the enemy and adds the kill score in one update when health reaches 0. Defense ([src/sim/defense.ts](src/sim/defense.ts), tuned in the `actions` settings): holding K on the ground guards (`runtime.blocking`, kept through blockstun; the held direction turns the guard); a guarded hit from the front does chip damage, blockstun and a short push instead of its reaction. Shift is a dodge: a short invulnerable sidestep in depth with a cooldown. **Grabs and throws** ([src/sim/grab.ts](src/sim/grab.ts), the `grab` sim system in [GrabSystem.tsx](src/components/GrabSystem.tsx), order `SYSTEM_ORDER.grab`, after the fighters move): with `input.actions.grab` on and at least one moveset row `when: "grabbing"`, the player grabs a free or stunned enemy in front (`actions.grab` tuning: range, depth, hold time) by walking into it for `contactTime` (`trigger: "contact"`, the default) or pressing grab beside it (`"button"`). The held enemy is a `held` reaction (light hits keep it held, a knockdown ends it) pinned in front of the player (`runtime.grab.target`; both fighters are busy) until it breaks free after `holdTime`, the player is hit, or a move with `throw` (direction `forward` / `back`, speed, lift, damage, `hitDamage`) reaches its active frames: the enemy is launched, knocked down, and keeps its speed until it lands (`runtime.thrown`), knocking down other enemies it flies into. Combat ignores throw moves' hitboxes. Enemy types with `grabbable: false` (the default HEAVY) can't be grabbed. The default moveset: while holding, attack knees (`grabKnee` → `grabKnee2` → `throwForward`), away + attack throws back, heavy throws forward. Damage to enemies from anywhere goes through `hurtEnemy` ([enemyDamage.ts](src/components/enemyDamage.ts)): KO sound and drops. An `air` move keeps the jump's arc and ends on landing (one air move per jump); a `lunge` move drives forward. Press H for the hitbox debug overlay (`showHitboxes` in the store): hurtboxes in green, active hitboxes in red, plus the HUD's frame-time readout.

### Content and tuning
Every gameplay definition and tuning value (speeds, jump, moves and their frame data, hit reactions, enemy types and AI archetypes, pickups, spawning, camera, stage, scoring, rules, and the levels) is data in the **default content pack**, the JSON files in [content/default/](content/default/) (`pack.json` metadata, `settings.json`, `moves.json`, `ai.json`, `enemy-types.json`, `pickups.json`, `levels.json`). Don't add gameplay literals to code. Times are seconds of game time. The runtime types are `GameConfig` in [src/config/defaults.ts](src/config/defaults.ts) and `Level` in [src/sim/level.ts](src/sim/level.ts); enemy type and AI archetype ids are plain strings.

**Gameplay code reads the active content through `getConfig()` / `getLevels()` from [src/content/active.ts](src/content/active.ts), at use time** (inside components, systems and store actions, never captured at module load), so the packs installed for a run take effect on the next scene mount. ESLint (`no-restricted-imports`) blocks `DEFAULT_CONFIG`, `config/levels` and `content/defaultContent` in components, store, sim and input; those static defaults (the default pack, validated at import) are for tests and tools. A snapshot test guards `DEFAULT_CONFIG`, so retuning the JSON means updating the snapshot deliberately (`npx vitest run -u`).

The `LoadingScreen` does the real load: `loadActivePacks()` (the default pack plus the enabled imported packs, through `loadContent` in [src/content/load.ts](src/content/load.ts)) validates and merges them, `setActiveContent` installs them, every glTF they use is fetched, then the game starts. Invalid content shows the error list with a way back to the menu instead of starting.

### Content packs (schemas and registry)
### Themes and props
Each level names a **theme** (the content's `themes`, typed `ThemeDef`): sky colour, optional fog, lighting (ambient, sun, hemisphere), ground and wall colours, and `backdrop` layers. `GameScene` applies sky, fog and lights; [Stage.tsx](src/components/Stage.tsx) takes its colours from the theme; [Backdrop.tsx](src/components/Backdrop.tsx) draws each layer's silhouettes (`skyline`, `hills` or `band`, generated from the layer's `seed` by `backdropShapes` in [src/sim/backdrop.ts](src/sim/backdrop.ts)) behind the back wall, shifted by `cameraX × parallax` every frame. Themes are visual only. The default pack ships `default` (the back alley) and `docks`; levels from packs older than schema v3 get `default`.

**Props** (the content's `props`, `PropDef` in [src/sim/props.ts](src/sim/props.ts)) are box or cylinder stage objects placed by a segment's `props` (`prop`, `at`, `depth`, optional `y` above the floor). `LevelDirector` places them in the store (`props`, stable ids, health from `breakable.health` or Infinity) when the level starts; [Props.tsx](src/components/Props.tsx) renders them, and `solid` ones are fixed colliders that fighters bump into and can stand on. The player's active hitboxes break `breakable` props in `CombatSystem` (`propBox`, once per move instance, `damageProp`), which may drop a pickup. A prop resting on a broken one doesn't fall, so don't stack breakables.

### Pack bundles, versions and the library
A shared pack is a **bundle**: a zip with `pack.json` at the top plus its asset files ([src/content/bundle.ts](src/content/bundle.ts)). `readBundle` checks size limits before inflating anything (`BUNDLE_LIMITS`: per file kind, total, file count), parses and validates the pack, and checks each asset: a safe relative path, present, `bytes` and SHA-256 `hash` matching, models must be `.glb`. Model `url`s in a bundle must be same-origin paths (`isLocalUrl`); anything else ships as an asset, so loading a pack never contacts a third party. `writeBundle` fills in sizes and hashes. Packs are data only; nothing in a bundle runs. `schemaVersion` upgrades go through [src/content/migrations.ts](src/content/migrations.ts) (`MIGRATIONS[n]` rewrites n → n + 1; `parsePack` migrates first, and a pack newer than the build is refused); bump `SCHEMA_VERSION` only with a migration and its test.

[src/content/library.ts](src/content/library.ts) holds imported bundles for the session: `installBundle` / `installBundleFromUrl` (must validate with the default pack and the enabled packs; the same id replaces the older install), `setPackEnabled`, `removePack`, export. Enabled packs load after the default pack in install order (later wins by id), bundled models get blob URLs, and each change re-validates and installs the active content; the store's `packs` and `contentError` drive the start menu's [PackPanel](src/components/PackPanel.tsx), and the menu won't start a run while `contentError` is set. Sample packs live as folders in `content/samples/<name>/` (pack.json plus assets); `npm run pack:sample` (run before `dev` and `build`) bundles them into `public/packs/<name>.zip`, which is generated and git-ignored. The shipped samples: Skeleton Remix changes stats, swaps the player to a CC0 skeleton model, adds a SKELETON enemy and The Crypt level; Stress Test is one level with 32 enemies at once, for `npm run perf`.

### Forge (the pack editor)
The start menu's FORGE button opens `gameScreen: 'forge'` ([src/components/forge/Forge.tsx](src/components/forge/Forge.tsx)). The creator's packs live in a **workspace** ([src/forge/workspace.ts](src/forge/workspace.ts)): `WorkspacePack { id, json, files (asset bytes by bundle path), updatedAt }`, with `newPack`, `duplicatePack`, `editPack` (the id is fixed at creation; renaming changes `name` only), `importBundle` (upgrades to the current schema; a taken id gets `-2`), `exportBundle`, and `validatePack` (errors from `buildRegistry([defaultPack(), json])`). [src/forge/storage.ts](src/forge/storage.ts) saves it in IndexedDB (`fight-forge-workspace`), with `memoryStore` for tests. "Play with this pack" exports and `installBundle`s it, then returns to the menu.

The content tree ([src/forge/tree.ts](src/forge/tree.ts), `buildTree`) lists every settings section, record (moves, AI, enemy types, pickups, themes, props) and level as `own`, `override` or `inherited` from the default pack; `overrideNode` copies the default's version into the pack, `removeNode` reverts or deletes, `addNode` adds a copy under a free id. The inspector is generated from the zod schemas: `fieldKind` / `defaultFor` / `labelFor` in [src/forge/schemaForm.ts](src/forge/schemaForm.ts) read a schema, and [SchemaForm.tsx](src/components/forge/SchemaForm.tsx)'s `Field` renders it (objects, numbers, colours, enums, tuples, arrays, records, unions and tagged unions; anything else as JSON). Values are edited immutably with `getIn` / `setIn` / `deleteIn` from [src/forge/paths.ts](src/forge/paths.ts), and a field shows the registry errors whose path (`pathString`) is its own. New editable content needs only a schema; don't hand-build forms for it.

Above the form, the player and enemy types get [FighterTools](src/components/forge/FighterTools.tsx) and moves get [MoveTools](src/components/forge/MoveTools.tsx), both drawing a [ModelPreview](src/components/forge/ModelPreview.tsx) (its own R3F `Canvas`, fighter facing +X, hurtbox and hitbox as boxes; a clip is posed at a given time when scrubbing). Fighter tools import a `.glb` into the pack (`addModelAsset`, then `gltfModelFor`), fit it to the body (`fitModel` from the model's bind-pose bounds), map clips to states from dropdowns, edit the player's moveset ([MovesetTools](src/components/forge/MovesetTools.tsx): a row per trigger, reorder, and a warning on rows an earlier one always beats, `shadowedTriggers`; helpers in [src/forge/moveset.ts](src/forge/moveset.ts)) and the light-attack combo (`comboChain` / `setComboChain` rewrite the combo root, the last plain attack row (`comboRoot`), and each move's `next`, copying default moves into the pack). Move tools show the move frame by frame at 60 Hz (`moveFrames`, `phaseAt`) with a phase timeline and cancel point, and a 2D side view where the hitbox is dragged and resized. Pack model assets preview through blob URLs (`usePreviewModel`). The pure parts are in [src/forge/fighter.ts](src/forge/fighter.ts). A tool edit on an inherited definition copies it into the pack first.

Enemy types also get [EnemyTools](src/components/forge/EnemyTools.tsx): sliders for the type's stats and its AI archetype's `reach` / `standOff` / `farReach`, the ATTACKS card ([AttacksTools](src/components/forge/AttacksTools.tsx): a row per attack and each one's chance at near and far range; the first edit turns `attackMove` into an `attacks` list, [src/forge/attacks.ts](src/forge/attacks.ts)) (ranges in `ENEMY_SLIDERS` / `AI_SLIDERS`, [src/forge/sandbox.ts](src/forge/sandbox.ts); an archetype edit affects every type that uses it), and a **sandbox** fight: the pack is installed, then `startSandbox(sandboxLevel(type, count))` plays a generated one-screen level (enemies placed beside the player, screen locked, goal past the lock) instead of the active levels. The store's `sandbox` holds that level; `GameScene` plays it when set, the HUD shows FORGE SANDBOX with FIGHT AGAIN / BACK TO FORGE, and `quitRun` (used by the results and pause menus) returns to the Forge from a sandbox or to the menu otherwise. The Forge remembers the selected pack and item across visits.

Levels get [LevelTools](src/components/forge/LevelTools.tsx), the level editor: an SVG timeline of the stage seen from above (X left to right, the back of the lane at the top) showing segments, fights (wave triggers, 🔒 when they lock), the goal, pickups, props and placed enemies. Objects are dragged (crossing a segment boundary moves them into that segment), a segment's end is dragged to resize it, a click sets the cursor, and the toolbar adds a fight, pickup, prop or goal at the cursor, splits the segment there, or adds one at the end. The selection gets quick controls (a fight's waves: who comes, from where, the lock) and its generated form. "Play from here" installs the pack and starts a sandbox with `levelFrom(level, cursor, spawnX)`: content behind the player is cut off, fights already passed are dropped, and the player starts at the cursor. "+ blank level" in the tree starts from `blankLevel()` (one segment and a goal). The pure parts (`levelObjects`, `moveObject`, `addObject`, `removeObject`, `resizeSegment`, `splitSegment`, `levelFrom`) are in [src/forge/level.ts](src/forge/level.ts).

The pack page has [PackInfoTools](src/components/forge/PackInfoTools.tsx): a cover image (`addImageAsset` adds a PNG, JPEG or WebP as a `texture` asset, `setCover` sets `meta.cover`; the start menu's pack list shows it) and every file in the pack with where it's used (`assetUsage` in [src/forge/assets.ts](src/forge/assets.ts)); a file still in use can't be removed. Bundles reject a texture that isn't an image (`imageType` in bundle.ts). The Input settings get [BindingsTools](src/components/forge/BindingsTools.tsx): the pack's bindings per device in Keyboard / Mouse / Controller tabs, keys added by pressing them and mouse and pad inputs from a list (`bindKey` takes an input off any other action on that device), or removed. Rules and everything else use the generated form; a test (`coverage.test.ts`) checks that every field of the pack schema has a form editor, so a schema change that would fall back to raw JSON fails it.

**Playtest loop** ([src/forge/playtest.ts](src/forge/playtest.ts)): a sandbox started from the Forge records its `playtest` origin in the store (the pack, and for "Play from here" the level as played and its `levelCut`). In a sandbox the HUD's ✎ EDIT (or the pause menu's EDIT IN FORGE) calls `editPlaytest`: `editing` freezes the scene (`isFrozen`), stops its Canvas drawing, and App renders the Forge over it while GameScene stays mounted; the input layer ignores keys meanwhile. The Forge's "▶ Back to the fight" installs the pack, then `planResume`: if the level played is unchanged (or it was an enemy sandbox) `resumePlaytest` carries on in the same scene, with the new tuning applied (Player and Enemy re-render when the store's `packs` change, and their steps read the fresh config); if the level changed, the sandbox restarts from where the player stood (`sceneProbe.playerX` from [src/sim/probe.ts](src/sim/probe.ts), which also gives each fighter's live runtime for headless checks), replaying a fight started within `REPLAY_FIGHT_WITHIN` behind them. "■ End playtest" is `quitRun`.

### Hosting and the backend
The game is a static site, deployed to GitHub Pages from `main` by [.github/workflows/deploy.yml](.github/workflows/deploy.yml) under the sub-path `/<repo>/` (Vite's `base` from `BASE_PATH`). Content names files shipped with the game by site paths (`/models/x.glb`); turn them into URLs with `siteUrl()` from [src/content/siteUrl.ts](src/content/siteUrl.ts) (the registry does it for model URLs), never by using the path directly. The sharing backend is decided in [docs/adr/0001-backend-and-hosting.md](docs/adr/0001-backend-and-hosting.md).

The **API** lives in [server/](server/) (its README lists settings and routes): Fastify, SQLite via `node:sqlite` (loaded with `createRequire`, since Vite can't bundle it), bundles and covers stored by SHA-256 ([server/blobs.ts](server/blobs.ts)). It imports the game's own `readBundle` / `buildRegistry` / `defaultPack`, so a published pack passes exactly the checks the game runs; keep `src/content` free of browser-only code. Sessions are an opaque token in an HttpOnly cookie (hash stored); state-changing requests need the `x-fight-forge: 1` header. `npm run server` runs it (`DEV_LOGIN=1` allows sign-in by name for development); its tests (`server/app.test.ts`, `fastify.inject`, in-memory store) run with the rest. The client is [src/net/api.ts](src/net/api.ts): with no `VITE_API_URL`, `apiEnabled()` is false and online UI stays hidden. The Forge's pack page has [PublishTools](src/components/forge/PublishTools.tsx): sign in, choose visibility, publish the current version (a published version must be newer; it offers the next patch version). The start menu's BROWSE PACKS opens the **gallery** (`gameScreen: 'gallery'`, [src/components/Gallery.tsx](src/components/Gallery.tsx)): search, sort, a creator filter, and a pack page with Play (`fetchBundle`, cached per version in the Cache API since bundles are immutable, then `installBundle` and `startRun` at the pack's first own level) and a share link. `?pack=<id>` (`linkedPack()`) opens straight to that pack's page. **Remix in Forge** (`remixBundle` in workspace.ts) copies a published pack into the workspace under a new id (`<id>-remix`), version 1.0.0, with `meta.remixOf` crediting the original; the server links a published remix to its original (`remix_of`), and pack pages show "Remix of" and the list of remixes. Likes are one per user (`POST /packs/:id/like`, sort `likes`). The gallery marks packs updated since this browser last played them ([src/net/played.ts](src/net/played.ts), localStorage). **Moderation**: anyone signed in can ⚑ Report a pack; moderators (`ADMINS` setting, `provider:name`) get a Reports panel ([Moderation.tsx](src/components/Moderation.tsx)) to take a pack down, dismiss reports or ban its owner, each logged in `moderation_actions`, and Take down / Put back on pack pages. A taken-down pack, or any pack of a banned user, is visible only to its owner (marked in PublishTools) and admins. Owners can remove their pack from the server. Limits are server-side: publishes and reports per user per hour, and writes per IP. Bundles check models with `glbProblem` (a whole glTF 2.0 file with no outside URIs) and audio with `audioType`; tests build models with `tinyGlb` from [src/test/glb.ts](src/test/glb.ts).

### Audio
Sound is content. The content's `sounds` (`SoundDef`, [src/audio/types.ts](src/audio/types.ts)) are `synth` (wave, pitch sweep, duration: no file needed) or `file` (an `audio` asset or a site URL); `music` is a looping `pattern` (tempo and tracks of space-separated notes like `A2 . C3 -`, parsed by [src/audio/notes.ts](src/audio/notes.ts)) or a `file`. `settings.audio` names the sound for each event (`hit`, `hurt`, `block`, `ko`, `pickup`, `clear`); a move can add `sound` (played as its active frames begin) and `hitSound`; a level can name `music`. [src/audio/engine.ts](src/audio/engine.ts) is the WebAudio engine: `playSound(id)` (from CombatSystem, Pickups, LevelDirector), `playMusic` / `stopMusic` (GameScene, per level), `duckMusic` while frozen, and `previewSound` / `previewMusic` for the Forge's [SoundTools](src/components/forge/SoundTools.tsx) (▶ Play, and "Use an audio file…" via `addAudioAsset`). Audio starts on the first click or key (`installAudioUnlock` in main.tsx). Master / music / effects volumes are a per-browser preference ([src/audio/volume.ts](src/audio/volume.ts)) set from [VolumeControls](src/components/VolumeControls.tsx) on the start menu (SOUND) and the pause menu. `audioLog` keeps the last sounds asked for, for headless tests.

### Performance
Crowds are budgeted ([src/sim/perf.ts](src/sim/perf.ts), [src/sim/budget.ts](src/sim/budget.ts)). [PerfMonitor](src/components/PerfMonitor.tsx) records every frame's time and the renderer's counts (it resets `gl.info` itself so shadow-map draws count) on `sceneProbe.perf`, shown by the HUD with H and read by `npm run perf`. Skinned glTF fighters register with the scene's `ModelBudget` (context from `GameScene`); [ModelBudgetDriver](src/components/ModelBudgetDriver.tsx) ranks them by distance from the player four times a second, and beyond `FULL_DETAIL_MODELS` (the player plus the nearest) a model stops casting shadows and animates at half rate. Enemy health bars are one set of instanced meshes ([HealthBars.tsx](src/components/HealthBars.tsx)), and hit sparks and dust are two instanced meshes in [Effects.tsx](src/components/Effects.tsx); prefer instancing over a mesh per enemy or per particle for anything that scales with the crowd.

### Game feel
`settings.feel` tunes (or turns off, each with `enabled`) hit-stop, screen shake, hit sparks, dust and damage numbers. The pure part is [src/sim/feel.ts](src/sim/feel.ts): one `FeelState` per scene (created by `SimLoopDriver`, read with `useFeel()`), fed by `feelHit` from CombatSystem on every landed hit (strength scales with damage). During a hit-stop (`feel.hold`) `SimLoopDriver` doesn't advance the loop and sets `HitStopContext`, which pauses physics in [ScenePhysics](src/components/ScenePhysics.tsx), so the fight resumes exactly where it was. `CameraRig` offsets the camera by `shakeOffset`; [Effects.tsx](src/components/Effects.tsx) ages effects (`stepFeel`) and draws sparks and dust as meshes and damage numbers as drei `Html` labels (no font download).

### Fighters and controllers
Player and enemies are both **fighters**. [src/components/FighterBody.tsx](src/components/FighterBody.tsx) is the one shared body: rigid body and collider, a `fighter:<name>` sim system (order `SYSTEM_ORDER.fighters`, before attacks and combat) that steps the hit reaction, asks a controller for an `Intent`, moves (or slides with knockback while reacting), jumps, updates facing and the fighter state machine, plus the model, attack tint, hurt flash and hitbox overlay. [Player.tsx](src/components/Player.tsx) and [Enemy.tsx](src/components/Enemy.tsx) are thin wrappers that supply the controller and start moves (the player's combo; an enemy's attack when it takes the slot). Both use `forwardRef<RapierRigidBody, …>` so `GameScene` holds refs to their bodies.

The pure logic is in `src/sim`: [fighter.ts](src/sim/fighter.ts) (`Intent`, `FighterStateName`, `nextFighterState`, `stepVelocity`, `updateFacing`, `FighterRuntime`, `isBusy`) and [controllers.ts](src/sim/controllers.ts) (`inputIntent` for the keyboard, `enemyIntent` for enemy AI). Each fighter's live `FighterRuntime` (state, facing, velocity, grounded, last intent, move, reaction, scale, hurtbox) is a mutable object updated every step; read it, don't mirror it into React state. Visuals (animation clock, model yaw) update in a render-rate `useFrame`.

Movement is applied via `setLinvel`, not forces: instant accel to `intent.move × walkSpeed`, then deceleration per 60 Hz step (`player.deceleration` 0.85 for the arcade slide, `enemy.deceleration` 0 for an instant stop); don't replace with damping without checking responsiveness. Enemy AI ([controllers.ts](src/sim/controllers.ts) `enemyIntent`) is shared by every archetype; each enemy type picks one with `ai` (the content's `ai`: `brawler`, `rusher` hangs back and lunges in with `rushPunch`, `tank` is a brawler whose type has `armor` (super armor against light hits), `flanker` goes behind the player and attacks only from there). An archetype is data: `approach` (`beside`, taking the other side if a closer enemy has this side's spot, or `behind`, detouring in depth), `reach`, `standOff` and `attackFrom`. Types can also set their own `attackMove`, or several **attacks** (`attacks: [{ move, range, weight, cooldown }]`, [src/sim/attacks.ts](src/sim/attacks.ts)): when it may attack, `pickAttack` chooses by weight among those that fit where it stands (`near` within `reach`, `far` beyond reach up to the archetype's `farReach`, or `any`) and are off cooldown, with a random seeded from the enemy id (`seededRandom`); a ready `far` attack lets the AI attack from far reach (`ctx.farAttack`, `attackRangeAt`). **Bosses** are enemy types with a `boss` block ([src/sim/boss.ts](src/sim/boss.ts); plan in [docs/plans/bosses.md](docs/plans/bosses.md)): `phases` ordered by health threshold (`below`) override speed, aggression, armor, AI, attacks and colour (`phaseStats`); on reaching one, Enemy cancels the move, goes invulnerable and stands for `transition.duration`, plays the `taunt`, pushes the player away within `transition.radius`, and queues the phase's `summon` (a scene-owned `SummonRequest[]` that LevelDirector spawns, placed ones beside the boss). `poise` turns knockdowns into staggers until `poise.hits` hits land within `poise.window` (`poiseHit`, on `runtime.poise`, applied in CombatSystem and to thrown bodies). A boss has its own attack slot (`runtime.ownAttackSlot`: no token needed, so it can attack alongside one helper) unless `sharesTokens`. The AI scales aggro range by the type's `aggression`, keeps `enemy.minSpacing` from other enemies (read directly from the shared `enemyRefs` Map), circles while every attack token is taken, and patrols outside aggro range. AI distances are planar (X/Z).

The grounded check is a short downward Rapier ray (`world.castRay`, excluding the fighter's own body, length `body.groundRayLength × scale`) plus near-zero vertical velocity. Collider half extents come from the fighter definition (`colliderHalfExtents`, default `body.colliderHalfExtents`, × scale).

### Character models
Each fighter definition has a `model: ModelRef` ([src/config/defaults.ts](src/config/defaults.ts)): `procedural` (the box `HumanoidModel`) or `gltf` (URL, scale, offset, `rotationY` to face -Z, `tintMaterials` recolored with the fighter's color, and a `clips` map from fighter state to clip name, optionally with a speed). [FighterModel.tsx](src/components/FighterModel.tsx) renders it; a glTF goes through `Suspense` and `ModelErrorBoundary`, with the box humanoid shown while loading and if it fails. [GltfModel.tsx](src/components/GltfModel.tsx) clones the cached scene per fighter (`SkeletonUtils.clone`, cloned materials) and plays the clip `resolveClip` ([src/sim/animation.ts](src/sim/animation.ts)) picks for `runtime.state`, with fallbacks (e.g. knockdown → hitstun → idle) and crossfades; action states play once. The state machine drives animation, never the reverse: hit ranges and timing don't depend on the art. `LoadingScreen` preloads every glTF the config uses. Model files live in `public/models/` with their licenses in `public/models/LICENSE.md`; only add permissively licensed (e.g. CC0) assets.

### Side-scrolling stage and camera
The game is a 2.5D beat 'em up. [src/components/Stage.tsx](src/components/Stage.tsx) is a long strip from x = 0 to `stage.length` with a depth lane `stage.depthBand` (z), a back wall, and solid ends. [src/components/CameraRig.tsx](src/components/CameraRig.tsx) is side-on: its `camera` sim system (after `fighters`) follows the player with a horizontal dead zone and, unless `camera.allowBacktrack`, never scrolls back; the render loop places the camera and moves the shadow-casting light with it. The shared `StageView` (`cameraX`, `maxCameraX`, `halfWidth` of the visible area) lives in `GameScene`. Fighters are kept in bounds by `FighterBody`'s `getBounds`: the player stays on screen (`screenBounds`), enemies stay on the stage and in the lane (`stageBounds`). Fighters face only left or right; depth-only movement keeps the last side. Enemies walk to their archetype's spot level with the player in depth, and attack only when within the archetype's `reach` in X and `enemy.depthTolerance` in Z. Periodic spawns walk in from just off a screen edge. The math is in [src/sim/stage.ts](src/sim/stage.ts) with tests.

### Controls
Bindings are data, per device (schema v4): the content's `input.bindings` has a `keyboard`, `mouse` and `gamepad` map, each from every action in `INPUT_ACTIONS` ([src/sim/input.ts](src/sim/input.ts): left, right, forward, backward, jump, attack, block, dodge, heavy, special, grab, run, pause, hitboxes) to that device's inputs: lowercase `KeyboardEvent.key` values (defaults: A/D or arrows to move, W/S or arrows for depth, Space, J, K, Shift, Escape, H), `MOUSE_INPUTS` (default: left button attacks, right blocks) or `GAMEPAD_INPUTS` (W3C standard-mapping names with Xbox labels, plus stick directions; raw `b7` / `axis2+` for non-standard pads). Migration 3 → 4 moves an old key map into `keyboard`. `input.actions` (schema v7) turns the optional actions on or off (`heavy`, `special`) and grabs (`grab.enabled`, `grab.trigger`: `contact` or `button`; only button grabs show a binding) and sets `run.mode` (`doubleTap`, `hold` the run button, or `both`) and `block.mode` (`hold` or `toggle`); `enabledActions` / `helpExtras` decide what the CONTROLS panel, the Forge's bindings card and the help text show, and the Forge's MOVESET card warns when heavy or special is on but no row or branch uses it (`unusedActions` in forge/fighter.ts). Defaults: heavy L / Y, special I / B, grab O / right stick click, run Q / left stick click (not Ctrl, since Ctrl+W closes the tab). The player's remapping (start menu CONTROLS panel, tabs for keyboard & mouse, where CHANGE takes a key, a click or the wheel, and controller) is a per-browser, per-device override in localStorage (`fight-forge.input-override.v2`; a v1 keyboard override is moved in once), merged on top by `getBindings()` in [src/content/bindings.ts](src/content/bindings.ts). The registry rejects an input bound to two actions on one device, a keyboard without left, right, attack or pause, and a gamepad without left, right or pause. Input goes through an **input layer**: `GameScene` owns one [InputManager](src/input/InputManager.ts) per scene (not React state), whose sources report named inputs (`key:j`, `mouse:left`; mouse buttons and the wheel only over the game's canvas, which also suppresses the context menu there) to a pure **action sampler** ([src/sim/actions.ts](src/sim/actions.ts)). The `input` sim system (first in `SYSTEM_ORDER`) samples an `ActionFrame` per step: each action's `held`, `pressed` and `released`, latched between steps so a tap shorter than a step is never dropped, plus a `move` vector; `Player` reads `frameControls(input.frame)`. The sampler remembers the last device used. Mapped keys get `e.preventDefault()`; blur and a trip to the Forge release everything, presses made while frozen are dropped, and the key map is rebuilt when packs are reinstalled. Double-tapping left or right and holding runs (`stepRunDetector`). Pause (`PauseMenu`) and the hitbox overlay (`HUD`) use `input.onPress`, which fires immediately, so they work while the sim is frozen. **Gamepads** ([src/input/gamepads.ts](src/input/gamepads.ts), pure parts in [src/sim/gamepad.ts](src/sim/gamepad.ts)): the first pad to press something is player 1; `readPad` polls `navigator.getGamepads()` and gives its inputs (`padInputs`: standard names, or raw `b7` / `axis2+` plus a best guess by position for non-standard pads). The InputManager polls every animation frame (frozen or not, so Start unpauses) and feeds the left stick through `padStick` (radial dead zone `input.analog.deadZone`, or the player's own from [src/input/prefs.ts](src/input/prefs.ts)) as the analog move: a stick walks at its tilt and runs past `input.analog.runThreshold`, keys and the d-pad override it. If the pad in use disconnects mid-fight, the game pauses. Rumble (`rumble()`, strength from `rumbleFor` and `settings.feel.rumble`, a player on/off toggle) fires from CombatSystem on hits the player takes or lands. Inputs held when the scene freezes are ignored until released (`suppressHeld`). The player's own comfort settings ([src/input/prefs.ts](src/input/prefs.ts), `loadControlPrefs`): rumble, dead zone, **toggle block** and **face the cursor** (standing still with keyboard and mouse, the fighter turns toward `input.pointerX`, the mouse's position over the canvas). The store's `inputDevice` and `padLabels` (from the pad's id: Xbox, PlayStation, Nintendo or generic names via `inputLabel`) make prompts (`deviceHelp`) name the last used device's buttons. [MenuPad](src/components/MenuPad.tsx) (always mounted, inactive in the Forge and while a fight runs) moves focus between the visible buttons with the d-pad or stick (`nextFocus` in [src/input/menuNav.ts](src/input/menuNav.ts)), A clicks, B resumes from pause or clicks a `data-menu-back` button. Controller capture in the CONTROLS panel and the Forge uses `usePadCapture`. The plan for the new actions is [docs/plans/extended-controls.md](docs/plans/extended-controls.md). On-screen help comes from `controlsHelp(bindings.keyboard)` and `actionLabel` / `inputLabel`; don't hard-code key names in UI text.

### Game flow: runs, lives, pickups, results
A **run** is played through the active levels (`getLevels()`, from `levels.json`) in order; the menu's level select starts a run at any level (`startRun`, via the loading screen). `GameScene` reads `getLevels()[levelIndex]` once per mount. Rules live in the `rules` settings (also `maxSimultaneousAttackers`, `friendlyFire`, which lets an attacking enemy's hitbox hit other enemies too, and `difficulty`: `damageTaken` multiplies damage to the player and `enemyHealth` every enemy's max health, via [src/sim/rules.ts](src/sim/rules.ts)): losing all health costs a life (`damagePlayer` refills health and bumps `respawnCount`; `Player` then drops back in mid-screen, invulnerable for `rules.respawnInvulnerability`, and the body blinks); losing the last life is game over, where a continue (`continueGame`, `rules.continues` per run) restores lives in place and RESTART LEVEL resets the run. Reaching the goal freezes the scene with a results overlay (score, time from the sim clock, KOs, lives); `nextLevel` keeps score, lives and run KOs and remounts the scene. **Pickups** (the content's `pickups`, heal or score; [src/sim/pickups.ts](src/sim/pickups.ts)) are placed by a segment's `items` (stable ids, placed when the level starts) or dropped by defeated enemies (`EnemyTypeDef.drop`, rolled in combat); [Pickups.tsx](src/components/Pickups.tsx) renders them and its `pickups` sim system collects any the player stands on.

### Levels, waves and screen locks
Enemies come from the level script, not a timer. A `Level` ([src/sim/level.ts](src/sim/level.ts)) is a list of segments; the stage length is the sum of their lengths (`levelLength`). Each segment holds triggers at an X offset: a `wave` trigger has one or more waves of spawn defs (`type`, `from` left/right/placed, optional `delay`, `depth`), optionally `lock`s the screen until all its waves are cleared, and a `goal` trigger ends the level (a goal reached while the screen is locked waits until the fight is won). A **`boss` trigger** (`enemy`: a type with a `boss` block, `from`, `offset`, `depth`, `music`, `intro`, `endsLevel`) always locks, spawns the boss and reports `bossStart`; when the boss is down it reports `bossDefeated` and, with `endsLevel` (the default, and then the level needs no goal), `complete`. LevelDirector puts the fight in `levelProgress.boss` (the HUD's [BossBar](src/components/BossBar.tsx): title, phase ticks, a delayed damage trail; the boss's small bar is hidden), shows the name card (`levelProgress.bossIntro`, which freezes the scene until it times out or any key or click skips it), switches music, and on the KO knocks out the remaining helpers, plays `feel.bossKo` (a long hit-stop, then slow motion: `slowFrame` lets only some rendered frames advance the sim and physics) and completes the level once that has played out (`feelBusy`); the results show BOSS TIME. The default pack's level 2 ends with BIG HARV (`HARV`: `bossSwipe`, `bossCharge`, `bossSlam`, the `roar` sound and `boss` music). `stepLevel` is pure and tested (including a headless playthrough); it returns `lock`, `unlock`, `waveStart` and `complete` events. [LevelDirector.tsx](src/components/LevelDirector.tsx) runs it as the `level` sim system: it spawns enemies (left spawns come from the right at the stage start), sets `view.lockX` (the camera holds there while locked), shows the HUD wave label and "GO →" prompt via `levelProgress` in the store, and calls `completeLevel`. The shipped levels are in `content/default/levels.json`. Per-type health, scale, speed, aggression and color come from the content's `enemyTypes`.

Brawler enemies patrol until they first come within aggro range, then stay engaged; enemies off screen (walking in, or left behind by the camera) are always engaged, so a locked fight can't stall on an enemy wandering off screen.
